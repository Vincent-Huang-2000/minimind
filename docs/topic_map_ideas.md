# 主题分布分析：多轮对话与长文本的改进想法

> 状态：想法，尚未实现。对应脚本 `scripts/topic_map.py`，现有用法见 [topic_map.md](topic_map.md)。

现在的实现把**每一行数据当作一条样本**：一行算一个向量、分到一个主题、在统计里算 1 次。这对单轮问答没问题，但对多轮对话和长文本，统计出来的"知识分布"会有偏差。本文记录几种改进做法，供后续实现时参考。

## 1. 背景：现在怎么处理

### 1.1 文本提取和截断

1. `extract_text()` 把一行转成一段文本：对话数据把所有 `user` 发言按顺序用换行拼起来；`--text_mode all` 时，`assistant` 的发言也拼进去。
2. 截断到 `--max_chars`（默认 1000 字）。
3. 向量模型只看前 `--max_seq_length`（默认 256）个 token。
4. e5 用平均池化得到向量，所以占 token 越多的内容，对向量的影响越大。

截断的原因：

- **模型有硬上限。** `multilingual-e5-small` 的位置编码只有 512 个，超过 512 个 token 根本处理不了，sentence-transformers 会自动截断。
- **256 是脚本为速度选的默认值。** 计算量随长度增长，注意力部分还是平方增长。不过 sentence-transformers 只把一批样本补齐到这一批里最长的那条，所以 `--max_seq_length` 只影响比它长的样本。
- **一个向量本来就装不下一长段文本。** 文本越长，平均池化混进的内容越多，向量越模糊。判断主题时，开头通常已经够用。
- **`--max_chars` 只是为了省 CPU。** 一段几万字的文本，最后只用前 256 个 token，没必要整段分词。

### 1.2 实测长度

用 e5 的分词器统计 `dataset/peek/` 里每个文件的前 20 行。样本很少，只看量级：

| 数据 | 模式 | token 数中位数 | 超过 256 个 token | 超过 512 个 token | 每 token 约多少字 |
|---|---|---:|---:|---:|---:|
| `pretrain_t2t_mini` | — | 173 | 7/20 | 0/20 | 1.5 |
| `pretrain_t2t` | — | 175 | 5/20 | 0/20 | 1.6 |
| `sft_t2t_mini` | user | 42 | 0/20 | 0/20 | 1.6 |
| `sft_t2t_mini` | all | 189 | 6/20 | 0/20 | 1.7 |
| `sft_t2t`（英文为主） | user | 25 | 0/20 | 0/20 | 3.6 |
| `sft_t2t`（英文为主） | all | 419 | 16/20 | 3/20 | 4.0 |
| `rlaif` | all | 307 | 13/20 | 0/20 | 1.7 |
| `agent_rl` | all | 327 | 14/20 | 2/20 | 1.8 |
| `dpo`（英文为主） | all | 432 | 15/20 | 4/20 | 4.3 |

能看出几点：

- 只取用户发言时（默认模式），几乎碰不到 256 的上限，截断基本没有影响。
- `all` 模式和预训练数据有相当一部分会被截断。
- **英文文本先被 `--max_chars` 截断。** 英文约 4 字符 1 个 token，1000 字符只有 230～250 个 token，还不到 256，见第 8 节。

用户发言的轮数（同样只看前 20 行）：

| 数据 | 平均每段对话的用户发言数 |
|---|---:|
| `sft_t2t_mini` | 4.75 |
| `agent_rl` | 2.8 |
| `rlaif` | 2.35 |
| `sft_t2t` | 1 |

### 1.3 训练时实际学到的内容

这一点和第 6 节的加权有关：

- **SFT**（`SFTDataset`）：先套用聊天模板，再截断到 `--max_seq_len`（默认 768）。loss 只算在 `assistant` 部分，包括思考过程 `reasoning_content`。另外有 20% 的概率随机插入一条 system prompt。
- **预训练**（`PretrainDataset`）：截断到 `--max_seq_len`（默认 340），全部 token 都算 loss。

## 2. 现在的问题

1. **跨话题的对话被平均掉。** 几个话题混在一个向量里，结果要么被分到篇幅最大的话题，要么落进按说话方式聚起来的簇。冒烟测试里（英文小模型，80 条，仅作参考），最大的主题占 41%，代表样本是：

   ```
   你的真实身份来自何处？
   你如何平衡效率与准确性？
   你今天过得怎么样？
   你最近有没有遇到什么有趣的事？
   ```

   这个主题的关键词是"真实 / 有没有 / 最近 / 今天"，反映的是说话方式，不是知识点。

2. **后面的轮次被截掉。** 主要发生在 `all` 模式和长文本里，见 1.2 节。

3. **统计单位是对话数。** 10 轮的长对话和 1 轮的短问答都只算 1 条。这既不等于"问了多少个问题"，也不等于"训练了多少 token"。

**要保留的优点**："那它的缺点呢？""为什么？"这类追问，单独看没有意义，和前文拼在一起才有意义。拆分时要想办法保住这一点。

## 3. 想法总览

| 想法 | 解决哪个问题 | 要重新向量化吗 | 改动量 | 建议顺序 |
|---|---|---|---|---|
| A. 只取第一轮提问 | 1（粗略）、2 | 要 | 很小 | 1 |
| B. 按轮拆分 | 1、2、3（按问题数统计） | 要 | 大：要引入"单元"这一层 | 2 |
| C. 按 token 数加权 | 3（按训练量统计） | 不要 | 中 | 3 |
| D. 多标签 | 1（跨话题的对话计入多个主题） | 不要（基于 B） | 小（基于 B） | 随 B 一起做 |
| E. 长文本分段 | 预训练数据的问题 1、2 | 要 | 中（复用 B） | 4 |

## 4. 想法 A：只取第一轮提问

**目的**：最快拿到一个基线。多数对话的话题由第一轮决定，这个结果可以和 B 对比，看后面的轮次对分布影响有多大。

**做法**：新增 `--text_mode first`，只取第一条 `role == "user"` 的消息。前面的 `system` 消息跳过。

**实现要点**：
- 只改 `extract_text()`：`roles` 的选择逻辑里加一个分支。
- `text_mode` 本来就在 `EMBED_KEYS` 里，续跑检查不用改。

**局限**：会漏掉后面换的话题。

## 5. 想法 B：按轮拆分

**目的**：统计"数据里问了哪些问题"，让跨话题的对话被正确拆开。

### 5.1 单元的定义

引入"单元"（unit）的概念，向量、主题都以单元为单位：

- 对话数据：每条内容非空的 `user` 消息是一个单元，用 `(row, turn)` 标识。`row` 是第几个非空行，`turn` 是这一行里第几条用户消息。
- 非对话数据（`text`、`question`）：一行一个单元，`turn = 0`，结果和现在一样。
- 单元的顺序固定为 row 升序、turn 升序。给定数据和参数，单元序列是确定的，续跑和 `keywords` 阶段都可以重新生成，不用整体存下来。

### 5.2 给短追问带上下文

- 新增 `--turn_context none|prev|first`：
  - `prev`：带上一条用户发言；
  - `first`：带第一条用户发言；
  - `none`：不带。
- 新增 `--context_max_chars N`：只有当前发言短于 N 字时才带上下文，拼成 `上下文\n当前发言`。这样既能处理"为什么？"这类追问，又不会把每一轮都拉向第一轮的话题。
- 默认值待定（见第 10 节）。建议先统计用户发言的长度分布，再定 N。

可选变体 `--text_mode turns_qa`：单元 = 用户发言 + 紧跟它的助手回答。注意 1.2 节的截断问题同样存在。

### 5.3 数据结构和改动

| 位置 | 改动 |
|---|---|
| `extract_text()` | 拆成"一行产出多个单元"的函数，返回 `[(turn, text), ...]` |
| `stage_embed` | 分片按单元计数（`--shard_size` 指单元数）。每片旁边写 `part_00000.idx.npy`（int32，形状 `(m, 2)`，存 `row, turn`）。续跑时重新生成单元序列，跳过前 `n_shards * shard_size` 个；删除过期分片时连同 `.idx.npy` 一起删 |
| `shard_paths()` | 正则 `part_\d{5}\.npy` 本来就不匹配 `.idx.npy`，不用改 |
| `meta.json` | 区分 `rows`（非空行数）和 `units`（单元数）；`turn_context`、`context_max_chars` 加进 `EMBED_KEYS` |
| `stage_cluster` | 基本不变，`2_labels.npy` 改为按单元对齐。可以顺便把各片的 idx 拼成 `2_units.npy`，方便后续使用 |
| `stage_keywords` | `want` 里存单元编号，通过 idx 映射到 `(row, turn)`，读数据时只提取那一轮（含上下文）。现在的条数检查 `seen != n` 改成"行数对 `meta['rows']`、单元数对 `len(labels)`" |
| `stage_report` | 每个主题显示两列：问题数（单元数）和涉及的对话数（去重后的 row 数，见想法 D） |

### 5.4 代价和风险

- 单元数约等于"行数 × 平均用户发言数"，`sft_t2t_mini` 的前 20 行约是 4.75 倍。不过每个单元都短，单条向量化更快，总耗时增加不到这个倍数，需要实测。
- **重复问题。** 比如 `sft_t2t_mini` 里大量问"你是谁"的变体，拆开后会让身份类主题变大。要不要去重，见第 10 节。
- 带上下文的启发式规则会有误判：短但独立的问题（"质数是什么？"）也会带上无关的上一句。

### 5.5 验证

- 用 `dataset/peek/` 的小样本在本地 CPU 上冒烟，按 AGENTS.md 的约定，不下载完整数据。
- 找一条已知跨话题的对话，确认它的几轮被分到不同主题。
- 对比整段对话模式和按轮模式下"说话方式类"主题的占比，预期会明显下降。
- 抽查"为什么？"这类追问，看带上下文后是否和前一轮落在同一主题。

## 6. 想法 C：按 token 数加权

**目的**：统计"训练的 token 落在哪些主题上"，这最接近模型实际学到的分布。不需要重新向量化，现有模式和 B 都适用。

### 6.1 权重的几种算法（`--weight_by`）

| 取值 | 含义 | 成本 |
|---|---|---|
| `rows` | 每条记 1，等于现在的做法 | 无 |
| `chars` | 按字数，作为 token 数的近似 | 低，不用分词器 |
| `tokens` | 用 MiniMind 自己的分词器（`model/`）数整条样本的 token | 中，要对全量数据分词 |
| `train_tokens` | 只数真正参与 loss 的 token：SFT 取聊天模板后前 `max_seq_len`（768）个 token 里的 assistant 部分（含思考过程）；预训练取 `min(tokens, 340)` | 较高；精确做法要复用 `SFTDataset.generate_labels`，逐条跑 Python 循环 |

`train_tokens` 可以先用近似算法：按顺序累加每条消息的 token 数，assistant 消息里落在前 768 个 token 以内的部分计入。随机插入的 system prompt 和空思考标签影响很小，可以忽略。

### 6.2 实现要点

- 新增 `weights` 阶段（纯 CPU）：读一遍数据，用 fast tokenizer 批量分词，写 `2_weights.npy`（float32，和 `2_labels.npy` 对齐）。全量分词的速度要在 Colab 上实测，必要时用多进程。
- 结合 B 时，单元的权重 = 这一轮之后助手回答的 token 数（loss 算在这里）；超出 768 个 token 的轮次记 0。
- `stage_report`：每个主题多一列"按 token 占比"，用 `np.bincount(labels, weights=w)` 计算。大类同理。

### 6.3 验证

- `chars` 和 `tokens` 两种加权算出的占比应该接近。
- 抽几条样本，把 `train_tokens` 的近似值和 `SFTDataset` 实际 labels 里非 `-100` 的个数对比。

## 7. 想法 D：多标签

**目的**：跨话题的对话，每个话题都计入。

两种做法：

- **D1：用单个向量取 top-m 个最近的主题中心**，相似度和最高值相差不到 δ 的都算。**不推荐**：混合向量是几个话题的平均，离它最近的中心不一定是组成它的那几个话题，可能是第三个更泛的主题。
- **D2（推荐）：基于 B，把各轮的主题汇总回对话。** 一段对话的主题集合 = 它所有单元的主题集合。几乎没有额外成本：
  - 报告里加"涉及该主题的对话数 / 占比"。各主题占比之和会超过 100%，要在报告里写明。
  - 可以加"平均每段对话涉及几个主题"。
  - 可选：统计最常一起出现的主题对。
  - 实现：对 `labels * n_rows + row` 做 `np.unique` 得到不重复的 `(主题, 对话)` 对，再按主题计数。

## 8. 想法 E：长文本分段（主要针对预训练数据）

**问题**：预训练数据的 `text` 本身也是多段内容拼起来的。比如 `pretrain_t2t_mini` 的第一条，前面是一首秋天的诗，后面是公司年会的节目创意。前 20 行里有 25%～35% 超过 256 个 token。按轮拆分对它没用，因为没有结构可拆。

**做法**：`--text_mode chunks`，把每条文本切成约 `--max_seq_length` 个 token 的片段，尽量在句号、换行处切，每段作为一个单元。可以直接复用 B 的单元、idx 和续跑机制。配合 C 时，按片段的 token 数加权。

**顺带修一个小问题：`--max_chars` 和 `--max_seq_length` 的关系。** 现在两者分开设置，而中文约 1.5 字 1 个 token，英文约 4 字符 1 个 token。默认的 1000 字对中文约是 600 个 token，够用；对英文只有 230～250 个 token，`--max_chars` 反而比 `--max_seq_length` 先截断。把 `--max_seq_length` 调到 512 时，如果忘了调 `--max_chars`，英文样本还是只用到约 250 个 token，等于白调。两种改法：
- 默认 `--max_chars = max_seq_length × 5`（按英文最坏情况）；
- 或者去掉 `--max_chars`，直接用向量模型的分词器截断，代价是 CPU 分词变多。

这个改动独立于其他想法，可以单独做。

## 9. 建议的实现顺序

1. **A**，以及第 8 节 `--max_chars` 的小修：改动最小，先拿到基线。
2. **B + D2**：核心改动，引入单元层；报告里同时出"问题数"和"涉及的对话数"。
3. **C**：独立于向量，三种模式都能用；先做 `chars` 和 `tokens`，`train_tokens` 视需要再做。
4. **E**：复用 B 的单元机制，用于预训练数据。

每一步都按现有约定：本地只用 `dataset/peek/` 的小样本冒烟，全量在 Colab 上跑。

## 10. 待定问题

- 短追问带上下文的阈值 N 和方式（`prev` 还是 `first`）：先统计用户发言长度的分布再定。
- 完全相同的问题要不要去重？可选做法：报告里同时显示去重前后的数量，或者加 `--dedupe` 选项。
- 报告默认按哪个口径排序（条数 / 问题数 / token 数）？
- `turns_qa` 变体值不值得做？它会重新引入截断问题。
- Agent RL 数据里工具定义所在的 `system` 消息，是否应该作为一种"任务类型"单独统计？目前两种模式都不取。
